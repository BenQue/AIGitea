# Issue tracker: AISoftPlatform Gitea

Issues, change contracts and pull requests live in the repository's configured private Gitea project. Resolve the
exact URL, owner and repository from the project profile or `origin`; never infer a different repository.

## Authority and boundaries

- Issue `#N` is the only request and tracking key.
- New work uses one immutable tuple: `change/N-short-description`, `docs/changes/N-short-description/`, `issue-N-short-description`, and one final PR with exactly one `Closes #N` line.
- Read and mutate Gitea only through the AISoftPlatform runtime/helper selected by the exact project profile.
- Do not use anonymous `404` as evidence that a private object does not exist.
- Agents may create local commits on the exact readable change branch. The Controller owns the PR-candidate handoff, `AWAITING_PR_CONFIRMATION`, fast-forward push, PR creation/update, CI and label projection. A human merges every manual PR. Only an explicitly authorized eligible routine-small PR may be merged by the independent exact-repository merger after all final-head hard gates pass. Deployment requires a separate authorization.
- Every triage comment starts with `> *This was generated by AI during triage.*`.

## Matt skill publication mapping

- `$triage #N` reads the complete Issue and uses the labels in `triage-labels.md`. Matt readiness never replaces the
  platform `approved` contract gate.
- `$to-spec #N` publishes to the active `spec` path declared by the Issue summary `documents` mapping. It updates the
  existing Issue with a link and `triage/ready-for-agent`; it does not create another Issue or set `approved`.
- `$to-tickets #N` publishes the approved vertical-slice graph to the active `plan` path. Ticket IDs are `T01`, `T02`,
  and so on; blocking edges use `blocked_by`. Default mode does not create child Issues.
- `$implement #N Txx` implements only that frontier ticket and may commit only on the current exact readable change branch. It must not
  push, create or merge a PR, change labels, or deploy.

Resolve document names with:

```bash
PYTHONPATH=codex/runtime python3 -m aisoft_loop.cli resolve-documents N --repo .
```

Publish a reviewed draft through the bounded adapter (the Gitea environment variables must identify this exact
repository):

```bash
PYTHONPATH=codex/runtime python3 -m aisoft_loop.cli publish-spec N /tmp/spec-draft.md --repo .
PYTHONPATH=codex/runtime python3 -m aisoft_loop.cli publish-plan N /tmp/plan-draft.md --repo .
```

New documents use `<role>-<short-description>-<YYMMDD>.md` and the same slug as branch/directory/worktree; numeric names are an evidence-derived legacy fallback. A legacy/readable pair or multiple slugs for one Issue is `CHANGE_NAME_CONFLICT`.

## Final PR candidate confirmation

Before push/create PR, persist a confirmation bound to the exact Issue, readable branch and `manual|routine-auto`
policy. Manual text must say CI repair may continue and then stop at `READY_FOR_REVIEW`; it must not contain an
auto-merge marker. Routine text must state exactly that in-contract CI repair may continue and, only when the final
head's required CI and every hard gate pass, controlled auto-merge is authorized. The authorization does not bind the
current SHA; the merge call must pin the final 40-character lowercase head SHA. Do not add a merge-policy label.

## Pull requests as a triage surface

PRs as a request surface: no. An explicitly named PR may still be inspected, but ordinary discovery only lists Issues.

## Wayfinding and multi-Issue mode

Wayfinding maps or child Issues require a complex parent spec that explicitly authorizes multi-Issue mode. Otherwise
keep decisions, spec, ticket graph, implementation and final PR bound to the original Issue.
