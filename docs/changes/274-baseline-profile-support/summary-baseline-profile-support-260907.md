## 问题/需求总结

Issue #271 的 `company-platform-baseline/v1` 把 Gitea health 目标、PostgreSQL patch 版本及 cluster/unit/storage identity 固定为一套候选拓扑。公司既有项目可能已按批准方案使用另一套安全拓扑，因此 v1 能诚实报告差异，却不能作为这些项目的可配置接管基线。

用户确认职责边界：AISoftPlatform 只提供通用能力；NewEMaint #79 在项目仓声明真实 SCM profile、部署步骤与现场证据。本 Issue 只实现通用、只读、fail-closed 的 v2 profile 支持，不写入 NewEMaint 的 IP、仓库名或数据库实例。

## 影响范围

新增独立 v2 collector、profile/inventory schema、使用说明、测试与本 Issue 文档。v1 collector/schema/示例保持字节不变；不修改治理 manifest、installer、CI、skill、公司服务器或任何项目仓。

## 初步方案与建议

v2 collector 只从自身同目录固定文件 `baseline-profile.json` 读取 canonical JSON；profile 本体、SHA-256 与 collector/source/host/evidence pins 一起进入 stdout envelope。profile 使用 closed schema，只允许私网或 loopback IPv4、固定二进制位置、受限 systemd unit/storage 形态和数值端口；collector 仍执行固定 argv、固定 health path、受限 HTTP target 与 metadata-only storage probe。

## 风险

- profile 被当成任意命令、URL、路径或内网扫描入口。
- profile 与回执摘要漂移，离线 verifier 无法复核 exact bytes。
- 修改 v1 导致已采集证据失去可追溯性。
- 项目 profile 合法被误写成现场部署或 mutation 授权。
