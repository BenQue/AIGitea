## 1. 方案概述与目标

构建一套**自托管的软件开发 + 半自动化部署运维平台**，核心思路是：

- 用本地电脑上的 **AI agent** 分析用户提交的 issue / change request（CR），产出开发方案。
- **所有质量门都由人工把关和批准**——不追求完全自动化。人工批准后，agent 才自动执行开发。
- 开发完成后在**本地测试环境**验证，再提交 PR。
- PR 合并后，由 **Gitea Actions（act_runner）** 执行确定性的部署流水线，先部署到**测试服务器**验证，人工确认后再**推送到不能上网的生产服务器**。

一句话概括分工：

> **AI 只碰「理解 issue、写代码」，act_runner 只碰「构建、迁移、重启」，人站在中间两道闸门（批准方案、合并 PR / 批准上生产）上。**

设计上刻意做到：**部署链路里没有 AI**。部署是确定性、可重复、可审计的脚本流程，不引入模型的随机性。

**落地策略：原型优先，逐级平移。** 不一上来就搭真实服务器，而是先在开发机上用 **OrbStack** 起一个 Ubuntu VM，把 Gitea、act_runner、Verdaccio 和测试应用环境全部塞进这一个 VM 里，在本地把整条流程（issue → 方案 → PR → CI → 部署 → 回滚）完整跑通。跑顺之后，再把**同样的安装步骤和同样的脚本**平移到公司内网服务器，最后到正式生产服务器。这样每一步扩展都建立在已验证的基础上，且部署脚本始终在与目标同构的真实 Ubuntu 上测试。

## 2. 整体架构

系统分三层，网络能力和职责各不相同：

```
┌─ 本地电脑（开发机 + AI agent）─────────────────────────────┐
│  · 开发机（编辑器 / 本地测试环境）                          │
│  · AI agent（Cowork + 定时任务）                            │
│     - 轮询 Gitea 读取 issue / CR                            │
│     - 用 skill 分析并产出开发方案 → 贴回 issue 评论          │
│     - 人工批准后：克隆仓库 → 改代码 → 本地测试 → 推分支 → 开 PR│
└───────────────────────────┬────────────────────────────────┘
                            │ git push / PR（仅到开 PR 为止，无合并权限）
                            ▼
┌─ 测试服务器（可上网）──────────────────────────────────────┐
│  · Gitea（仓库、issue、PR、Actions）                        │
│  · act_runner（CI/CD 执行器，host 模式）                    │
│  · Verdaccio（私有 npm 缓存代理）← 弱网问题的解药            │
│  · Node(nvm) · PM2 · PostgreSQL(测试库) · Redis · Nginx     │
│                                                             │
│  流水线（act_runner 执行）：                                │
│   PR 事件  → 安装依赖 → lint → 测试 → 构建（验证能编译）     │
│   合并 main→ 构建自包含制品 app-<sha>.tar.gz                 │
│            → 部署到本机测试环境(PM2 reload)                  │
│            → 迁移测试库 → 健康检查                           │
│                                                             │
│  人工验证测试环境 ✔                                          │
└───────────────────────────┬────────────────────────────────┘
                            │ 人工触发 promote：rsync over SSH
                            │（测试机"推"，生产机不"拉"）
                            ▼
┌─ 生产服务器（不能上网 / air-gapped）───────────────────────┐
│  · 接收制品 → pg_dump 备份 → 解压                           │
│  · prisma migrate deploy（纯本地 SQL，不联网）              │
│  · pm2 reload（零停机）→ 健康检查 → 失败自动回滚            │
│  · Nginx 反代 · PostgreSQL(生产库) · Redis（全部本地）      │
│  · 运行时（Node/PM2/PG/Redis/Nginx）一次性装好，之后不动    │
└─────────────────────────────────────────────────────────────┘
```

**关键约束回顾：**

- 生产服务器**不能访问网络** → 生产机永远不安装任何东西，只接收自包含制品。
- 测试服务器**可以上网**，但 `docker build` 常断线 → **整体去 Docker 化**，改用 PM2 + 自包含制品，配 Verdaccio 缓存解决弱网。
- 本地电脑是开发机和 AI agent 所在地，agent 靠桌面定时任务驱动。

### 2.1 环境演进阶梯：本地 OrbStack 原型 → 内网 → 生产

上面的三层**逻辑架构不变**，改变的只是它在不同阶段的**物理落地方式**和**推进顺序**。先在开发机（macOS）上用 OrbStack 起 Ubuntu VM，把整套东西塞进一个 VM 跑通原型，再逐级平移到真实服务器：

```
阶段 1：本地原型（全部在开发机的 OrbStack VM 内）
┌─ 开发机（macOS）──────────────────────────────────┐
│  开发机 + AI agent（宿主机上，通过 VM 端口访问）   │
│  ┌─ OrbStack VM: gitea-ci (Ubuntu, 有网)────────┐ │
│  │  Gitea + act_runner + Verdaccio              │ │
│  │  测试应用环境（PM2 + PG + Redis + Nginx）     │ │
│  └───────────────────────────────────────────────┘ │
│  ┌─ OrbStack VM: prod-sim (Ubuntu, 断网)────────┐ │ ← 可选：模拟离线生产
│  │  只接收制品 → 迁移 → pm2 reload → 回滚         │ │
│  └───────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────┘
                     │ 脚本/流程跑通后，原样平移（无 Docker，纯二进制+脚本）
                     ▼
   阶段 2：公司内网服务器            阶段 3：正式生产服务器（离线）
   ┌ Gitea + act_runner ─┐          ┌ 只接收制品 → 备份 ─┐
   │ + Verdaccio + 测试   │   ──►    │ → 迁移 → reload     │
   │   环境（CI/CD 中枢） │          │ → 健康检查 → 回滚   │
   └──────────────────────┘          └─────────────────────┘
   （OrbStack VM 保留为本地沙盒，改部署脚本先在这里验证再动内网）
```

**为什么这样走：**

- **环境一致性（核心好处）**：OrbStack VM 跑的是真实 Ubuntu，与内网/生产服务器同构。部署脚本里的 `systemctl`、目录路径、用户、`rsync`、`pm2` 行为都和真机一致——从根上避免"开发机测试成功、服务器部署失败"。而且你是在**真实 runner 执行的真实流水线**里验证，不只是单独跑脚本。
- **零风险试错**：VM 可随时快照、销毁重建，搞砸了删掉重来，不碰任何真实资产。
- **离线彩排**：再起一个断网的 `prod-sim` VM，就能在本地把"离线 promote 到生产"这一最容易翻车的环节完整彩排一遍（OrbStack 可为 VM 关闭网络来模拟 air-gap）。
- **平移成本极低**：因为一切都是二进制 + 脚本、没有 Docker，从 VM 到真机就是"同样的安装步骤 + 同样的脚本"，**制品和流水线 YAML 一个字都不用改**，只改各机器本地 `.env` 里的地址。

> 平移时，[操作指南 B（测试服务器）](#8-操作指南-b测试服务器) 的所有步骤先在 `gitea-ci` VM 上执行一遍即为原型；之后在内网服务器上原样再执行一遍即为内网环境。[操作指南 C（生产服务器）](#9-操作指南-c生产服务器不能上网) 先在断网的 `prod-sim` VM 上彩排，再对真实生产机执行。

## 3. 角色与权限切分（最重要）

这是整个方案敢用、能用的前提。三方权限严格隔离：

| 角色 | 能做什么 | **不能**做什么 |
|------|----------|----------------|
| **桌面 AI agent** | 读 issue、写评论、推送 feature 分支、开 PR | ❌ 合并 PR　❌ 生产库密码　❌ 服务器 SSH　❌ 触发部署 |
| **人（你）** | 批准方案、review 并合并 PR、触发上生产 | —（唯一有生产变更决定权的角色）|
| **act_runner** | 构建、跑迁移、重启服务；持有部署密钥/DB 密码（存 Gitea Secrets）| ❌ 不理解代码　❌ 只在合并/人工触发后按 YAML 执行 |

要点：

1. agent 用的是一个**独立的 Gitea 机器人账号**（不是你的 owner 账号），token 权限最小化，范围仅到「开 PR」。它能造成的最大破坏就是提一个烂 PR。
2. **人工闸门有两道**：① issue 里批准开发方案（防止 agent 朝错误方向做一整轮，省返工）；② PR 合并 + 上生产批准（防止烂代码进生产）。
3. 部署密钥、DB 密码只存在于 **Gitea Actions Secrets** 和**生产机本地**，agent 和仓库代码里都没有。

## 4. 端到端工作流

```
用户提 issue / change request
        │
        ▼
① 桌面定时任务轮询 Gitea API（如每 15 分钟）
        │
        ▼
② agent 读取 issue → 用 skill 分析 → 把「开发方案」作为评论贴回 issue
        │
        ▼   ← 【人工闸门 1】你在 issue 里回复批准（如 /approve 或打 label）
        │
③ agent 克隆仓库 → 改代码 → 本地测试环境验证 → 推 feature 分支 → 开 PR
        │
        ▼
④ Gitea Actions 在 PR 上自动跑 CI（lint + 测试 + 构建验证）
        │
        ▼   ← 【人工闸门 2a】你 review PR，Merge 到 main
        │
⑤ 合并触发部署流水线：构建自包含制品 → 部署到测试服务器 → 迁移测试库 → 健康检查
        │
        ▼   ← 【人工验证】你在测试服务器上验证功能
        │
⑥ 【人工闸门 2b】你手动触发 promote：把同一个制品 rsync 到生产机
        │
        ▼
⑦ 生产机：pg_dump 备份 → 解压 → prisma migrate deploy → pm2 reload → 健康检查 →（失败回滚）
```

> **注意：制品只在测试服务器构建一次。** 部到测试和上生产用的是**同一个制品的同样字节**，绝不为生产重新构建，从而保证「测过的就是上线的」。

## 5. 核心设计原则

**原则 1：一次构建，传自包含制品。**
在能上网的测试服务器上把应用打包成"自带全部依赖"的制品（`app-<sha>.tar.gz`），生产机只解压、迁移、重启，**永不安装任何东西**。制品包含：前端构建的静态文件、后端代码、生产依赖 `node_modules`、Prisma 生成的 client 与引擎二进制、以及 `prisma` CLI（供迁移用）。

**原则 2：制品与环境配置分离。**
制品本身不含任何环境信息。数据库地址、Redis 地址、密钥等全部放在各机器本地的 `.env`，由 PM2 运行时注入。同一个制品在测试和生产用不同 `.env` 运行。

**原则 3：整体去 Docker 化。**
对 Node.js 栈 + air-gapped 生产环境，Docker 带来的正是你遇到的痛点（构建联网易断、镜像传输到离线生产机麻烦）。PM2 + 制品能拿到八成隔离好处，却绕开这些痛点。

**原则 4：部署链路无 AI。**
合并之后的一切是同一套脚本每次跑出完全一样的结果，可重复、可审计、可回滚。

**原则 5：任何变更都可逆。**
迁移前必备份，制品保留多版本，健康检查失败自动回滚。air-gapped 生产环境出事没法轻易联网补救，这条是底线。

## 7. 操作指南 A：本地开发机

本地电脑承担开发和 AI agent 两个角色。

### 7.1 基础开发环境

```bash
# 安装 nvm 并固定 Node 版本（与服务器保持一致，示例用 20）
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
nvm install 20 && nvm use 20
node -v   # 记下大版本，测试机/生产机要一致

# 全局工具
npm i -g pm2

# 项目根目录固定 Node 版本
echo "20" > .nvmrc
```

### 7.2 给 agent 建 Gitea 机器人账号

1. 在 Gitea 里新建一个专用账号，例如 `ci-bot`（**不要**用你的 owner 账号）。
2. 把 `ci-bot` 加为目标仓库的 Collaborator，权限设为 **Write**（能推分支、开 PR，但**不给** Admin，也不设为能直接合并保护分支）。
3. 生成个人访问令牌（Settings → Applications），**Scopes 只勾选**：`read:issue` / `write:issue`（评论）、`read/write:repository`（推分支、开 PR）。不要勾 admin 类权限。
4. 把 token 保存在本地 agent 能读到的安全位置（如本地环境变量 / 密钥管理），**不要进仓库**。

### 7.3 本地测试环境

- 本地跑一份 PostgreSQL + Redis（或连测试库的独立 schema），供 agent 改完代码后本地验证。
- 项目里准备 `.env.local`（本地库地址等），不进仓库。

### 7.4 用 OrbStack 起原型 VM（阶段 0 的载体）

在开发机（macOS）上创建与目标服务器同构的 Ubuntu VM。这是"原型优先"策略的落地载体：

```bash
# 装好 OrbStack 后，创建一个 Ubuntu VM 作为 CI + 测试一体机
orb create ubuntu gitea-ci

# 可选：再建一个用于彩排离线生产的 VM
orb create ubuntu prod-sim

# 进入 VM 执行命令（语法以 OrbStack 当前文档为准）
orb -m gitea-ci sudo apt update
```

进入 VM 后，直接套用后面的操作指南：在 `gitea-ci` 内按 [操作指南 B](#8-操作指南-b测试服务器) 装 Gitea + act_runner + Verdaccio + 测试环境；在 `prod-sim` 内按 [操作指南 C](#9-操作指南-c生产服务器不能上网) 准备离线部署目标。

关键提示：

- 宿主机（开发机 + agent）通过 VM 域名访问 Gitea，OrbStack 会给每个 VM 自动分配可从宿主访问的地址（形如 `gitea-ci.orb.local`）。
- 彩排离线部署时，先在 OrbStack 里**关闭 `prod-sim` 的网络**模拟 air-gap，验证"自包含制品能在完全离线的机器上完成 `migrate deploy` + `pm2 reload`"。
- VM 随时可 `orb delete gitea-ci` 重建，试错零成本；跑通后做个快照留档。

## 8. 操作指南 B：测试服务器

测试服务器可上网，承载 Gitea、act_runner、Verdaccio、测试环境。以下命令基于 Ubuntu。

### 8.1 基础运行时

```bash
sudo apt update
# Node（用 nvm 或 nodesource，版本与本地一致）
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs postgresql redis-server nginx git
sudo npm i -g pm2
```

### 8.2 安装并注册 Gitea（若尚未装）

> 已装可跳过。Gitea 官方为单二进制，无需 Docker。

```bash
# 下载二进制（示例路径，版本以官方最新为准）
```

### 8.3 安装并注册 act_runner（host 模式）

```bash
# 下载 act_runner 二进制到 /usr/local/bin/act_runner 并 chmod +x
cd /opt && sudo mkdir -p act-runner && cd act-runner

# 在 Gitea 后台 (Site Admin → Actions → Runners) 获取注册 token，然后：
sudo act_runner register \
  --instance http://localhost:3000 \
  --token <REGISTRATION_TOKEN> \
  --name test-runner \
  --labels ubuntu-latest:host   # host 模式：直接在宿主机执行，不用 Docker
```

生成 `.runner` 配置后，用 systemd 托管：

```ini
# /etc/systemd/system/act_runner.service
[Unit]
Description=Gitea Act Runner
After=network.target

[Service]
User=gitea-runner
WorkingDirectory=/opt/act-runner
ExecStart=/usr/local/bin/act_runner daemon
Restart=always

[Install]
WantedBy=multi-user.target
```

```bash
sudo useradd --system --home /opt/act-runner gitea-runner
sudo chown -R gitea-runner:gitea-runner /opt/act-runner
sudo systemctl enable --now act_runner
```

> **host 模式说明**：job 直接在宿主机上跑 shell 命令，能直接操作本机的 PM2 服务和文件，最适合单机自用。缺点是构建过程与测试环境共享机器——将来若要更强隔离，可换 container 模式 + SSH，流水线 YAML 几乎不用改。

### 8.4 安装 Verdaccio（弱网救星）

```yaml
    publish: $authenticated
    proxy: npmmirror

    access: $all
    publish: $authenticated
```

让 CI 构建使用 Verdaccio（项目根目录 `.npmrc`，可进仓库）：

## 9. 操作指南 C：生产服务器（不能上网）

核心思想：**运行时一次性装好，之后再也不联网。**

### 9.1 一次性安装运行时（趁有网时或用离线 .deb 包）

如果生产机曾短暂可联网，先装好这些；若从头就离线，则用 `apt-get download` 在测试机上把 .deb 及依赖下载好，拷贝到生产机 `sudo dpkg -i *.deb` 安装：

```bash
# Node（与测试机同一大版本，关键！）、PostgreSQL、Redis、Nginx
sudo apt install -y nodejs postgresql redis-server nginx
sudo npm i -g pm2         # PM2 全局，之后不再动
pm2 startup               # 生成开机自启（按提示执行输出的命令）
```

> **为什么 Node 版本必须一致**：Prisma 引擎、bcrypt 等原生模块按平台和 Node 版本编译，制品带的二进制在版本不匹配的机器上会崩。

### 9.2 生产库、目录、环境文件

```bash
sudo -u postgres createdb app_prod
sudo -u postgres psql -c "CREATE USER app_prod WITH PASSWORD 'xxxx';"

sudo mkdir -p /opt/app-prod/releases /opt/incoming /opt/db-backups
```

生产环境变量（只存在于生产机，**绝不进仓库**）：

```bash
# /opt/app-prod/.env
DATABASE_URL=postgresql://app_prod:xxxx@127.0.0.1:5432/app_prod
REDIS_URL=redis://127.0.0.1:6379
NODE_ENV=production
PORT=8080
```

### 9.3 Nginx（生产环境）

与测试服务器配置相同，`root` 指向 `/opt/app-prod/current/frontend`，反代端口指向生产 PM2 进程。建议配合 Let's Encrypt 上 TLS（若生产机彻底离线，则用内网自签证书）。

### 9.4 SSH 接收通道

- 在测试机上生成部署专用密钥对，把公钥加入生产机某个受限部署用户（如 `deployer`）的 `~/.ssh/authorized_keys`。
- `deployer` 通过一条极窄的 sudoers 规则只允许重启目标服务（见 [第 14 节](#14-安全设计)）。

## 10. CI/CD 流水线与脚本模板

所有工作流放在仓库 `.gitea/workflows/` 下，本身也走 PR 评审——连"部署流程怎么改"都经过人工把关。

### 10.1 CI：PR 上跑测试与构建验证

```yaml
# .gitea/workflows/ci.yml
name: CI
on:
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 安装依赖（走 Verdaccio）
        run: npm ci
      - name: Lint
        run: npm run lint
      - name: 单元测试
        run: npm test
      - name: 构建验证（确认能编译）
        run: npm run build
```

### 10.2 构建 + 部署到测试环境：合并 main 触发

```yaml
# .gitea/workflows/deploy-test.yml
name: Build & Deploy to Test
on:
  push:
    branches: [main]

jobs:
  build-and-deploy-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 安装依赖
        run: npm ci

      - name: 构建前端 + 生成 Prisma client
        run: |
          npm run build                       # 前端 dist / next build
          npx prisma generate                 # 生成 client + 引擎（binaryTargets 已配）

      - name: 打包自包含制品
        run: ./scripts/pack.sh ${{ github.sha }}

      - name: 部署到本机测试环境
        env:
          DATABASE_URL: ${{ secrets.TEST_DB_URL }}
        run: ./scripts/deploy-local-test.sh ${{ github.sha }}

      - name: 健康检查
        run: ./scripts/health-check.sh http://127.0.0.1:8080/health
```

### 10.3 `scripts/pack.sh` — 生成自包含制品

```bash
#!/usr/bin/env bash
# 用法: pack.sh <sha>
set -euo pipefail
SHA="$1"
OUT="/opt/artifacts/app-${SHA}.tar.gz"
STAGE="$(mktemp -d)"

# 后端：只保留生产依赖 + prisma（迁移用）
npm ci --omit=dev
npx prisma generate

# 组装制品目录
mkdir -p "$STAGE/backend" "$STAGE/frontend"
cp -r src package.json node_modules prisma "$STAGE/backend/"   # 含 @prisma/client + 引擎
cp -r dist/* "$STAGE/frontend/" 2>/dev/null || true            # Vite: dist/；Next: 见备注
cp ecosystem.config.js "$STAGE/"

tar -C "$STAGE" -czf "$OUT" .
echo "制品已生成: $OUT"
rm -rf "$STAGE"
```

> **Next.js 备注**：在 `next.config.js` 设 `output: 'standalone'`，构建后把 `.next/standalone`、`.next/static`、`public` 一并打进制品，Next 会自动裁剪出所需的最小 node_modules。
>
> **Prisma 迁移依赖备注**：`prisma migrate deploy` 需要 `prisma` CLI 与迁移引擎。把 `prisma` 放进 dependencies（而非 devDependencies），或在 pack 时显式保留，确保离线生产机能执行迁移。

### 10.4 `scripts/deploy-local-test.sh` — 部署到测试环境

```bash
#!/usr/bin/env bash
# 用法: deploy-local-test.sh <sha>
set -euo pipefail
SHA="$1"
BASE=/opt/app-test
REL="$BASE/releases/$SHA"

mkdir -p "$REL"
tar -C "$REL" -xzf "/opt/artifacts/app-${SHA}.tar.gz"

# 迁移测试库
( cd "$REL/backend" && DATABASE_URL="$DATABASE_URL" ./node_modules/.bin/prisma migrate deploy )

# 切换软链 + 零停机重启
ln -sfn "$REL" "$BASE/current"
cd "$BASE/current/backend"
pm2 reload ecosystem.config.js --env test || pm2 start ../ecosystem.config.js --env test
pm2 save
```

### 10.5 `scripts/health-check.sh`

```bash
#!/usr/bin/env bash
# 用法: health-check.sh <url>
set -euo pipefail
URL="$1"
for i in $(seq 1 10); do
  if curl -fsS "$URL" >/dev/null; then echo "健康检查通过"; exit 0; fi
  sleep 2
done
echo "健康检查失败: $URL" >&2
exit 1
```

### 10.6 `ecosystem.config.js` — PM2 配置

```javascript
module.exports = {
  apps: [
    {
      name: 'app-api',
      script: 'backend/src/server.js',   // 或 next standalone 的 server.js
      cwd: __dirname,
      instances: 2,                       // cluster 模式支持零停机 reload
      exec_mode: 'cluster',
      env: {},                            // 通用默认
      env_test:       { NODE_ENV: 'test',       PORT: 8080 },
      env_production: { NODE_ENV: 'production',  PORT: 8080 },
    },
  ],
};
```

> 生产/测试的敏感值（DATABASE_URL、REDIS_URL）由各机器本地 `.env` 提供，PM2 通过 `dotenv` 或启动前 `export` 注入，不写进这个进仓库的文件。

### 10.7 `scripts/promote-to-prod.sh` — 人工触发上生产

> **由你在测试服务器上手动运行**（而非自动流水线），因为上生产是高风险、air-gapped 的动作，应是一次深思熟虑的人工操作。

```bash
#!/usr/bin/env bash
# 用法: promote-to-prod.sh <sha>
set -euo pipefail
SHA="$1"
ARTIFACT="/opt/artifacts/app-${SHA}.tar.gz"
PROD=deployer@prod-server.internal

echo ">> 传输制品到生产机（测试机推）"
rsync -avz -e ssh "$ARTIFACT" "$PROD:/opt/incoming/"

echo ">> 在生产机上执行部署"
ssh "$PROD" "sudo /opt/app-prod/deploy-prod.sh $SHA"
```

### 10.8 生产机 `deploy-prod.sh` — 离线部署 + 备份 + 回滚

> 此脚本**预先放在生产机**上（不依赖网络），由 promote 通过 SSH 调用。

```bash
#!/usr/bin/env bash
# 位置: /opt/app-prod/deploy-prod.sh   用法: deploy-prod.sh <sha>
set -euo pipefail
SHA="$1"
BASE=/opt/app-prod
REL="$BASE/releases/$SHA"
source "$BASE/.env"

echo ">> 迁移前备份生产库"
pg_dump "$DATABASE_URL" | gzip > "/opt/db-backups/pre-${SHA}-$(date +%s).sql.gz"

echo ">> 解压制品"
mkdir -p "$REL"
tar -C "$REL" -xzf "/opt/incoming/app-${SHA}.tar.gz"

echo ">> 数据库迁移（纯本地，不联网）"
( cd "$REL/backend" && DATABASE_URL="$DATABASE_URL" ./node_modules/.bin/prisma migrate deploy )

echo ">> 切换并零停机重启"
PREV=$(readlink "$BASE/current" || true)
ln -sfn "$REL" "$BASE/current"
cd "$BASE/current/backend"
pm2 reload "$BASE/ecosystem.config.js" --env production || pm2 start "$BASE/ecosystem.config.js" --env production
pm2 save

echo ">> 健康检查（失败自动回滚）"
if ! "$BASE/health-check.sh" "http://127.0.0.1:8080/health"; then
  echo "!! 健康检查失败，回滚到 $PREV"
  ln -sfn "$PREV" "$BASE/current"
  pm2 reload "$BASE/ecosystem.config.js" --env production
  exit 1
fi
echo ">> 上生产完成: $SHA"
```

## 11. AI Agent 编排

agent 跑在本地电脑，靠**桌面定时任务**驱动，人工始终在环。

### 11.1 定时任务：轮询与分析

- 用桌面 agent 的定时任务能力，例如每 15 分钟轮询一次 Gitea。
- 通过 **Gitea MCP 连接器或 REST API**（用 `ci-bot` token）拉取带特定 label（如 `needs-analysis`）的新 issue / CR。
- agent 用 **skill** 分析 issue，产出结构化的「开发方案」，作为评论贴回该 issue，并把 label 改为 `awaiting-triage`（最终标签集见《阶段 2.6》）。

> 提示：桌面定时任务依赖本机开着、Cowork 在运行。电脑关机则轮询暂停——对个人场景可接受，心里有数即可。

### 11.2 自定义 skill：让方案稳定贴合你的项目

用 **skill-creator** 写一个专属 skill，把这些编码进去：

- 仓库结构、技术栈约定（Express + Prisma + React/Next 的分层）
- 测试要求（改动必须带测试，CI 卡合并）
- 数据库迁移规范（任何 schema 变更走 Prisma migration，禁止手改）
- 分支命名、PR 描述模板

这样 agent 每次出的方案风格一致、可执行，而不是每次都不一样。

### 11.3 人工批准后：自动开发

- 你在 issue 里批准（如回复 `/approve` 或打 `approved` label）。
- agent 检测到批准 → 克隆仓库 → 建 feature 分支 → 按方案改代码 → 在**本地测试环境**跑测试 → 推分支 → 用 `ci-bot` 开 PR，PR 描述里链接回原 issue。
- 此后进入 CI 流程，由你 review 和合并。**agent 到开 PR 为止，不参与合并与部署。**

## 12. 数据库迁移与备份

**Prisma 配置（`schema.prisma`）** —— air-gap 的两个必配项：

```prisma
generator client {
  provider      = "prisma-client-js"
  // 覆盖所有目标平台，否则制品带的引擎在该机跑不起来
  // OrbStack VM(Apple Silicon, arm64, OpenSSL 3.0) → linux-arm64-openssl-3.0.x
  // amd64 真机 Ubuntu 22.04(OpenSSL 3.0) → debian-openssl-3.0.x（20.04/OpenSSL1.1 用 ...openssl-1.1.x）
  binaryTargets = ["native", "linux-arm64-openssl-3.0.x", "debian-openssl-3.0.x"]
}
```

> 部署前确认生产机的 OpenSSL 版本（`openssl version`），选对应的 target。

**迁移执行**：

- 生产环境只用 `prisma migrate deploy`（**不是** `migrate dev`）。它只按仓库里 `prisma/migrations/` 已有的迁移文件跑 SQL，**不联网、不生成新迁移**。
- 迁移文件由开发时 `prisma migrate dev` 生成并随代码提交、走 PR 评审。

**备份**：

- 生产机迁移前**自动 `pg_dump`**（已内置在 `deploy-prod.sh`）。
- 另设每日定时 `pg_dump` 全量备份，保留最近 N 份，最好异地放一份。air-gapped 生产库无法轻易联网补救，备份是底线。

## 13. 弱网 / 断网应对方案

针对你 `docker build` 常断线的根因（每次构建都联网重拉依赖，一抖动整层重来）：

**短期最快见效三步：**

1. **换国内镜像**：`npm config set registry https://registry.npmmirror.com`
2. **架 Verdaccio 缓存代理**（见 8.4）：包拉过一次就永久本地化，构建从此基本不看网络脸色。
3. **给 Prisma 配引擎镜像**（否则 Prisma 装依赖时下载引擎二进制也会断）：

```bash
export PRISMA_ENGINES_MIRROR=https://registry.npmmirror.com/-/binary/prisma
export PRISMA_BINARIES_MIRROR=https://registry.npmmirror.com/-/binary/prisma
```

落地后，构建从"docker build 里反复联网"改为"测试服务器上 `npm ci`（走本地 Verdaccio 缓存）+ `vite build` / `next build`"，稳定性与 Docker 不是一个量级。

**生产机彻底离线的依赖问题**：由"一次构建、传自包含制品"原则解决——生产机永不 `npm install`，制品自带全部 `node_modules` 与 Prisma 引擎。

## 14. 安全设计

**最小权限 token**：agent 用独立 `ci-bot` 账号，token scope 仅到读写 issue + 推分支 + 开 PR，无合并、无 admin。

**密钥隔离**：

- 部署密钥、生产 DB 密码只存在于 **Gitea Actions Secrets** 和**生产机本地 `.env`**。
- 仓库代码、agent 本地都不含生产密钥。

**窄 sudoers 规则**：act_runner / deployer 需要重启服务，但绝不给 root。只放行重启目标服务这一条：

```
# /etc/sudoers.d/deployer
deployer ALL=(root) NOPASSWD: /bin/systemctl reload myapp, /bin/systemctl restart myapp
```

（若用 PM2 reload 则无需 systemctl 权限；此规则用于需要 systemd 托管的场景。）

**TLS**：Nginx + Let's Encrypt 给 Gitea 与对外应用上 https；生产机若彻底离线则用内网自签证书。

**分支保护**：在 Gitea 里对 `main` 开启保护——要求 PR 评审、CI 通过才能合并，禁止直接 push。

## 15. 回滚策略

| 层面 | 回滚方式 |
|------|----------|
| 应用代码 | 制品按 `<sha>` 多版本保留在 `releases/`，切回上一个软链 + `pm2 reload` 即可 |
| 部署过程 | `deploy-prod.sh` 健康检查失败**自动**切回 `$PREV` 并重启 |
| 数据库 | 迁移前 `pg_dump` 备份；必要时用备份恢复（注意与已回滚代码的兼容）|
| 迁移设计 | 尽量写**向后兼容**的迁移（先加列不删列、分两步下线字段），降低回滚时数据不兼容风险 |

## 16. 分阶段实施路线图

路线图按「原型优先，逐级平移」组织：**先在开发机的 OrbStack VM 里把全流程跑通（阶段 0–2），再平移到公司内网（阶段 3），最后到正式生产（阶段 4）。** 每一步都建立在已验证的基础上。

### 本地原型（全部在开发机的 OrbStack VM 内完成）

**阶段 0 — 起 VM 并打地基**
- [ ] OrbStack 创建 `gitea-ci` VM（Ubuntu），可选再建 `prod-sim` VM
- [ ] `gitea-ci` 内装好 Node(nvm)/PostgreSQL/Redis/Nginx/PM2
- [ ] 装 Gitea 并开启 Actions；装 Verdaccio，配 npmmirror 上游，项目 `.npmrc` 指向本地缓存
- [ ] 装并注册 act_runner（host 模式），systemd 托管

**阶段 1 — 打通 CI（先不碰部署）**
- [ ] 建示例仓库，放 `ci.yml`，提个 PR 验证 lint/test/build 能跑通
- [ ] 验证 Verdaccio 缓存生效（断网重试构建仍成功）
- [ ] 配好 Prisma `binaryTargets`（含 VM 的 Ubuntu 平台），`prisma generate` 成功

## 17. 待部署时细化的开放问题

这些可在实操中边做边定：

1. **测试覆盖现状**：自动开发只有在有测试且 CI 卡合并时才安全。现有项目测试到什么程度？先补关键路径测试。
2. **测试环境隔离度**：测试环境与 Gitea/act_runner 同机，CI 构建可能与测试服务抢资源——是否需要给 runner 上资源限制，或后续把 runner 拆到 container 模式。
3. **前端选型统一**：React+Vite 与 Next.js 的制品打包方式不同（静态文件 vs standalone），建议每个项目固定一种，`pack.sh` 相应分支。
4. **promote 触发方式**：目前设计为人工在测试机跑 `promote-to-prod.sh`。将来可选：推 `release-*` tag 触发一个需人工 approve 的 workflow。
5. **生产机初始化联网窗口**：若生产机从未联网，需在测试机上用 `apt-get download` 准备好离线 .deb 包集。
6. **Prisma 引擎精确 target**：以生产机实际 `openssl version` 为准最终确认 `binaryTargets`。
7. **多项目复用**：以上脚本可抽成模板仓库或一个内部 CLI，供多个项目复用，减少重复配置。
