# 全新项目需求发现与滚动阶段规划

本方法用于已登记、已采用平台使用发布包的全新项目，从已有想法或需求材料形成项目规划，再交给现有 Issue 流程。
规划尺度是：**当前阶段详细，下一阶段有轮廓，远期保留方向。**
事实、假设、决定和验证证据的通用要求见 [共享工程原则](engineering-principles.md)；Issue 交付仍按项目内
`.aisoft/platform-usage.md` 与 [路由表](route-policy.md)。这里不增加授权主键、机器状态或确认点。

## 1. 找到合适入口

| 当前情况 | 下一步 |
|---|---|
| 只有想法，项目尚未采用发布包 | 先整理用户自己的本地笔记，再按 [上手指南](getting-started.md) 完成采用；可以从空仓开始 |
| 已有需求或方案，没有可维护实现 | 引用已有结论与证据，找出冲突和当前阶段缺口，复用有效材料 |
| 小型单阶段项目 | 简报、路线图、阶段记录可合并在一个文件；只有一张 Issue 时直接进入其会话 |
| 多领域、多阶段项目 | 保留必要全局边界与浅层路线图，只展开当前阶段 |
| 已有代码或已交付项目的增量需求 | 转 [项目对齐](project-align.md) 或现行 Issue 流程，不重置已有合同与证据 |

采用之前不启动本方法。想法阶段只用当时实际可用、不依赖 tracker 的能力：已安装 Matt 插件的用户可显式
使用 `grill-me`；采用前没有项目技能落点的用户用普通对话整理。不配置 Local-markdown 或 `.scratch` tracker，
不运行 `triage`、`to-spec`、`to-tickets` 或 `wayfinder`。采用后由首张规划 Issue 将本地笔记整理进项目规划入口。

接入顺序按 [onboarding-runbook](onboarding-runbook.md)，本方法不选择或改变项目 `change_control`。
接入验收中需要应用代码的项目，在首阶段退出证据中引用，不能把尚未执行写成已通过。
技术栈和交付选择写入项目使用合同 §4 的扩展点，如 `AGENTS.md` 项目事实与 `.aisoft/architecture.json`；规划资料只链接。

## 2. 一个入口，明确资料归属

层级为“项目 → 阶段 → Issue → Txx”。这里的阶段是规划阶段，与 [issue-session-flow](../../issue-session-flow/SKILL.md)
的阶段同义；它不是 `change_control` 的交付阶段，也不形成新的批准对象。

在项目 `AGENTS.md`「项目事实」的「项目规则」条目登记规划入口，建议为 `docs/planning/README.md`，由该入口链接
简报、路线图和当前阶段记录。可以复用已有项目文档或将三者合并；项目规划资料不放在 `docs/changes/` 下。
采用时填写项目事实即可登记入口。已采用项目需补写时，由首张规划 Issue 按 complex 准备治理 proposal，依
[runbook §6](onboarding-runbook.md#6-判级接入) 交独立受控步骤应用，再 fresh run 采用；普通实现会话不编辑约束本次运行的 AGENTS。

| 资料 | 记录什么 | 不重复保存什么 |
|---|---|---|
| 项目简报 | 使用者、问题证据、预期价值、成功指标、范围与非目标、约束和关键假设 | 已有术语、架构决定、业务规则的正文 |
| 项目路线图 | 稳定阶段 ID、目标、范围轮廓、依赖、未知、退出证据、阶段进展和 Issue 链接 | Issue 状态、授权或 Txx 任务图 |
| 当前阶段记录 | 阶段目标、输入、范围、决定指针、假设、验证方式、Issue 切分与依赖、结果和调整理由 | 各 Issue 的完整合同和执行证据 |

已接受的决定按项目 `docs/agents/domain.md` 归位：术语进 `GLOSSARY.md`，架构决定进 `docs/adr/`，业务规则进相关
产品或变更合同。规划资料仅保留指针。每张 Issue 的合同、状态和实际证据仍以该 Issue 为准。

**写入归属：** 首张规划 Issue 创建规划资料；后续调整和阶段结果由规划或收口 Issue 写入，其 git_scope 列明文件。
多 Issue 阶段中的实现 Issue 只链接阶段记录，不改规划资料；调度会话只起草，把确认后的文字放进承载它的规划 Issue
正文，不进入它的 worktree 实现。阶段记录合并前，同阶段其它 Issue 将该规划 Issue 列为依赖。
单 Issue 的项目或阶段由它兼任规划 Issue，把规划文件列入自己的 git_scope，资料与阶段结果随同一 PR 交付。
术语与 ADR 也只由拥有对应范围的 Issue 会话写入。

## 3. 先发现问题，再确定规划深度

读取已有材料和负责人已确认的方向，显式使用 Matt `grill-me` 补影响当前决策的缺口：谁使用、现有工作方式、困难、
期望结果、成功指标、非目标和约束。已有回答直接引用；来源与日期可核对的事实、负责人决定、未验证假设分开记录。
访谈结束按下方模板写出资料，并经 §2 的 Issue 写入路径持久化，不能只停留在聊天里。

| 范围 | 要明确到什么程度 | 暂不展开 |
|---|---|---|
| 当前阶段 | 可观察结果、范围/非目标、必要设计与接口、依赖/风险、退出证据；各 Issue 的可测 AC 草案与依赖 | 不影响当前边界的后续细节；完整 Issue 合同在各自会话生成 |
| 下一阶段 | 只展开紧接的一个阶段：目标、主要能力、依赖、关键未知、进入前要补的证据 | 详细设计、任务、工期、完整 Issue 清单 |
| 远期 | 方向、业务结果、关键约束或可能依赖 | 顺序、完整需求、方案、任务与日期承诺 |

访谈按同样深度收口：当前问到可执行，下一阶段问到轮廓，远期分支记假设并停下追问。
下一阶段变为当前之前，不为其交付范围创建 Issue；为下一阶段补证据的发现或验证工作可安排为当前阶段 Issue。
一个阶段对应一个有退出证据的可观察结果，通常对应一张调度路线图。AI 提议边界，负责人作决定并留下依据。

全局设计只处理当前必须知道的系统边界、领域语言、数据所有权、权限/隔离、外部接口和不可逆选择。决定归位后，
记录理由、前提与复核触发条件；其余用假设表达，不提前设计所有服务和数据结构。
关键假设写明影响、验证阶段、证据和失效波及范围。若未知阻碍当前范围界定，先安排有结果判据的发现/验证 Issue；
远期未知不自动阻塞独立的当前工作。调查、原型和验证的受管仓库写入同样受 Issue 合同约束。

## 4. 当前阶段转入既有交付流程

阶段需求收敛后，按可验证结果拆 Issue。多 Issue 使用 [issue-session-flow](../../issue-session-flow/SKILL.md) 调度，
单 Issue 直接进入其会话。调度路线图保留名称、一句话目标、判级、依赖、可与谁并行、状态及推荐顺序；
项目阶段视图仅链接这些 Issue，不复制其状态，也不替各 Issue 定级。

按既有授权经 broker 逐张创建 Issue，带流程入口标签，正文包含 AC、依赖和规划入口/阶段链接。规划草案本身不授予
建仓、批量建 Issue、派发新会话、实施或部署权限。各 Issue 会话先读取阶段记录，再独立判级、形成合同与查路由。

- production complex 按 Matt `to-spec → to-tickets` 形成映射 spec/plan；`to-tickets` 只作用于一张已存在的 Issue。
- small 与 development complex 保持现行简化规则；development 使用 Issue AC 与合成 T01，不产生 plan 文件。
- 子 Issue 路由卡以 `aisoft resolve-route` 输出为准。当前工具不读取 G1 的第三个条件；G1 语义仍以路由表为准，
  需要澄清时另立 Issue，不在本方法内改写。执行与完成核验直接读取路由表的 provider 映射。

负责人决定下一阶段何时成为当前阶段，参考进入证据和本阶段结果。独立 Issue 的收尾可与转换重叠；转换不是新闸门。
转为当前后按 issue-session-flow 的“大阶段任务”入口展开，仍只使用现有合同/启动与最终 PR 两个确认点。

## 5. 核对结果并滚动调整

阶段结果核对四件事：Issue 的真实状态和证据、跨 Issue 的接口/集成结果、阶段目标需要的观察、尚未验证的假设。
PR 合并、测试通过、部署可达和业务验收分别记证据；Issue 全关闭不能单独证明阶段目标完成。

更新路线图时保留阶段 ID，写调整原因、证据和依赖影响。未批准的未来范围逐步细化；若变化影响已批准 Issue 的
范围、AC 或架构/安全边界，经 broker 评论通知该 Issue，不改其正文，由其 owner 停止受影响部分并按既有合同变更处理。
调度会话不改别人的合同或 worktree；独立且不受影响的 Issue 可继续。规划资料的最终修改仍按 §2 归属进入规划/收口 Issue。

新会话从项目 AGENTS 的「项目规则」找入口，再读当前阶段、关联 Issue 原始合同、最新证据和未决项即可恢复。
不依赖原聊天或某个技能内部缓存。

## 6. 按能力缺口选择已有技能

| 需要的能力 | 本方法使用的入口与产物 |
|---|---|
| 问题发现、阶段需求澄清 | 显式调用 Matt `grill-me`，按 §3 深度收口；结果进入规划资料 |
| 需要第三方提供事实 | 显式调用 Matt `to-questionnaire`；问卷与阶段资料放在一起，并由阶段记录链接 |
| 核查一手资料 | Matt `research`；记录来源与结论，产物由阶段记录链接并经所属 Issue 写入 |
| Issue 内方案、规格、任务、执行与审查 | 按该 Issue 的 [路由表](route-policy.md)，本方法不重复选择 |
| 多 Issue 协调与恢复 | `issue-session-flow` |

本方法的规划与编排只使用上述入口。其它可见但会自建项目/阶段/计划状态的技能包，需另立适配 Issue 才能用于本方法。
Matt `wayfinder` 虽被 `ask-matt` 推荐给全新项目，也不是这里的入口；其地图与 child Issue 仍受项目
`docs/agents/issue-tracker.md` 的 “Wayfinding and multi-Issue mode” 约束，接入前不能用 `.scratch` 地图替代规划入口。
`grill-me`、`to-questionnaire`、`to-spec`、`to-tickets` 均须显式调用；本方法不安装技能或改变 pin。

## 7. 最小模板

仅将需要的部分复制到所属项目 Issue 的获批文件中。入口建议为 `docs/planning/README.md`，实际路径以 AGENTS 的
「项目规则」为准；三种资料可合成一个文件或链接项目既有文档。所有尖括号内容均为待填写的占位值。

### 项目入口与简报

```markdown
# <项目名称> 规划入口

- 资料位置：简报 <本文件章节或路径>；路线图 <章节或路径>；当前阶段 <阶段 ID 与记录位置>
- 资料拥有者：<规划或收口 Issue 链接>
- 使用者与问题：<使用角色、现有做法、主要困难>
- 事实与来源：<证据、来源、日期>；已确认方向：<负责人决定及依据>
- 预期价值与成功指标：<结果、观察方式、结果判据>
- 范围与非目标：<本项目做什么、不做什么>
- 约束与全局边界：<约束；GLOSSARY、ADR、业务合同、项目事实的指针>
- 关键假设：<假设表位置；尚缺哪些证据>
```

### 浅层路线图

```markdown
| 阶段 ID / 深度 | 名称与可观察目标 | 范围轮廓 | 依赖与未知 | 退出证据 | 阶段进展 / Issue 与证据链接 |
|---|---|---|---|---|---|
| <当前 ID / 当前> | <可验证结果> | <范围与非目标> | <依赖、关键未知> | <观察方式与判据> | <已知进展、缺口、Issue 链接> |
| <下一 ID / 下一> | <目标与主要能力> | <能力轮廓> | <依赖、进入前要补的证据> | <结果轮廓> | <尚未展开；当前补证 Issue 链接> |
| <远期 ID / 远期> | <方向与业务结果> | <方向> | <关键约束或可能依赖> | <待进入近期再细化> | <依据或假设链接> |

推荐顺序与理由：<当前可启动部分、依赖关系；远期顺序尚未确定时明示>
调整记录：<日期、原因、证据、受影响阶段与依赖；保留原阶段 ID>
```

### 当前阶段记录

```markdown
# <阶段 ID>：<名称>

- 可观察目标与退出证据：<结果、观察方式与判据>
- 输入事实与负责人决定：<来源、日期；已有结论指针>
- 范围与非目标：<当前边界>
- 必要设计决定：<数据/权限/接口及不可逆选择的 ADR、术语或业务合同指针>

| 假设 | 影响 | 验证所在阶段 | 证据 / 结果 | 失效时受影响范围 |
|---|---|---|---|---|
| <待验证判断> | <当前或后续影响> | <阶段 ID> | <已有证据或待补> | <阶段 / Issue / 决定指针> |

| Issue | 可测 AC 草案 / 交付结果 | 依赖 | 合同与证据链接 |
|---|---|---|---|
| <Issue 链接> | <一个可验收结果> | <依赖 Issue；无则写无> | <原始合同与验证位置，不复制 Txx 或状态> |

- 阶段结果：<Issue 证据、跨 Issue 集成结果、目标观察、剩余假设与缺口>
- 调整与后续：<证据、决定、影响；下一阶段的进入证据与负责人决定>
- 本记录写入归属：<规划或收口 Issue；单 Issue 时由其兼任>
```
