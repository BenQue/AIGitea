# Issue tracker: AISoftPlatform Gitea

Issues, change contracts and pull requests live in the repository's configured private Gitea project. Resolve the
exact URL, owner and repository from the platform's broker manifest or `origin`; never infer a different repository.

## Authority and boundaries

- Issue `#N` is the only request and tracking key.
- New work uses one immutable tuple: `change/N-short-description`, `docs/changes/N-short-description/`, `issue-N-short-description`, and one final PR with exactly one `Closes #N` line.
- Read and mutate Gitea only through the AISoftPlatform host-access broker for the exact manifest project.
- Do not use anonymous `404` as evidence that a private object does not exist.
- Agents may create local commits on the exact readable change branch. The session owns the PR-candidate handoff and `AWAITING_PR_CONFIRMATION`; only after the second confirmation does it fast-forward push, create/update the PR, follow CI and project labels through the broker. A human merges every PR (routine merge left in #391). Deployment requires a separate authorization.
- Every triage comment starts with `> *This was generated by AI during triage.*`.

## Matt skill publication mapping

- `$triage #N` reads the complete Issue and uses the labels in `triage-labels.md`. Matt readiness never replaces the
  platform `approved` contract gate.
- `$to-spec #N` publishes to the active `spec` path declared by the Issue summary `documents` mapping. It updates the
  existing Issue with a link and `triage/ready-for-agent`; it does not create another Issue or set `approved`.
- `$to-tickets #N` publishes the approved vertical-slice graph to the active `plan` path. Ticket IDs are `T01`, `T02`,
  and so on; blocking edges use `blocked_by`. Default mode does not create child Issues.
- The plan is executed as the route card says: Codex runs `$implement #N Txx`; Claude and Cursor execute the mapped plan with
  superpowers `executing-plans`. Either way one frontier ticket at a time, committing only on the current exact readable change
  branch, and never push, create or merge a PR, change labels, or deploy.

Resolve document names with:

```bash
PYTHONPATH=codex/runtime python3 -m aisoft_loop.cli resolve-documents N --repo .
```

Publish a reviewed draft through the bounded adapter (the Gitea environment variables must identify this exact
repository):

```bash
PYTHONPATH=codex/runtime python3 -m aisoft_loop.cli publish-spec N /tmp/spec-draft.md --repo .
PYTHONPATH=codex/runtime python3 -m aisoft_loop.cli publish-plan N /tmp/plan-draft.md --repo .
```

New documents use `<role>-<short-description>-<YYMMDD>.md` and the same slug as branch/directory/worktree; numeric names are an evidence-derived legacy fallback. A legacy/readable pair or multiple slugs for one Issue is `CHANGE_NAME_CONFLICT`.

## Derived Issues

A problem found mid-task becomes a new Issue instead of extra scope in the current one. The authoring session must
write four things into the Issue body: the originating Issue and session, the target project repository, at least one
testable acceptance criterion, and every known blocking Issue number (write `none` when there is none). Dependencies
belong in the body -- session context is compacted, an Issue is not.

`gitea.issue.create` writes the flow entry label in the same call that creates the Issue: `needs-analysis`, or
`triage/needs-triage` when the session asks for the triage entrance. A new Issue therefore starts at the flow
entrance rather than in an inbox nobody reads.

The default claimant of a derived Issue is the coordination session, which judges and dispatches it during the
open-Issue sweep. With no coordination session, the authoring session opens the Issue and dispatches it itself.

## Final PR candidate confirmation

Before push/create PR, get a confirmation bound to the exact Issue and readable branch. The candidate text must say
CI repair may continue and then stop at `READY_FOR_REVIEW`; it must not contain an auto-merge marker. The
authorization does not bind the current SHA. Do not add a merge-policy label.

## Pull requests as a triage surface

PRs as a request surface: no. An explicitly named PR may still be inspected, but ordinary discovery only lists Issues.

## Wayfinding and multi-Issue mode

Wayfinding maps or child Issues require a complex parent spec that explicitly authorizes multi-Issue mode. Otherwise
keep decisions, spec, ticket graph, implementation and final PR bound to the original Issue.

## v1.3.1 evidence and orchestration boundaries

`pr` prepares Summary / Evidence / Merge Danger content for the existing final candidate. Preserve exactly one
`Closes #N`, the mapped summary path, dependencies, authorization marker and exact Issue/branch/policy. State
Before/After observations with their SHA, command/artifact and evidence layer; missing evidence stays explicit.
Describe reversibility, rollback and affected users/modules. Preparing this text never submits the PR.

`retro` is explicitly selected by Matt source/path through `aisoft-matt-workflow`; it returns candidates for human
review, without automatic governance changes. `implement-spec` is not enabled for writing orchestration here.
The session implements one frontier ticket at a time and performs remote mutation only after confirmation.
